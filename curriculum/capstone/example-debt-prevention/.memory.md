# Skill-Level Memory — Skill Debt Prevention

**Skill**: skill-debt-prevention  
**Type**: Meta-skill (governs the skill bank)  
**Origin**: Lesson 5 extension — emerged from student analysis of hvac-control regression

---

## Why this skill exists

The hvac-control regression (80% → 20%) wasn't a model failure or a bad prompt.
It was a governance failure: a skill was created from one successful trajectory,
registered without cross-environment validation, and never re-tested after the
initial deployment. The MUSE paper has Merge + Forget operations, but they are
reactive — triggered after failure is observed. This skill is the proactive version.

The lesson: a skill bank without governance degrades exactly like a codebase without
code review. The individual additions look fine. The accumulation is what kills you.

---

## Lessons Learned

### Lesson 1: Pre-mortem at creation is undervalued
**Situation**: During pilot with students, skills that ran a pre-mortem before registration
caught 3 of the 5 trajectory-specific assumptions that would have caused drift.
Skills that skipped this step failed re-validation within 2 weeks.  
**Why it matters**: The assumptions that break a skill in month 3 are almost always
visible at creation time — they're just invisible to a creator who has only seen one successful run.  
**Implication**: Procedure 1 pre-mortem should be mandatory, not optional.

### Lesson 2: "Quarantine" is emotionally hard for students to implement
**Situation**: Students consistently proposed infinite revival periods or no pruning at all.
The difficulty: it feels like killing something you created.  
**Why it matters**: Skills that avoid quarantine because of emotional attachment — not
because of evidence — create exactly the kind of debt the protocol is trying to prevent.  
**Implication**: Frame quarantine as ICU, not cemetery. The skill is recoverable.
The 14-day window exists to gather evidence, not to perform an execution.

### Lesson 3: Overlap detection needs to be semantic, not keyword-based
**Situation**: Two skills with different names (one about "debugging reasoning", one about
"finding root cause in code") were functionally identical. Keyword search missed the overlap.  
**Why it matters**: A skill bank with duplicates forces the retrieval system to choose between
two near-identical options — and it often chooses the wrong one based on surface similarity.  
**Implication**: Procedure 3 should use semantic comparison (embed and compare), not
just name/description matching.

### Lesson 4: Archived ≠ deleted — this is the most important distinction
**Situation**: Several students conflated the Sunset Protocol's "prune" step with permanent deletion.
One group deleted their test skill and couldn't recover when they needed to reference it.  
**Why it matters**: Skills carry `.memory.md` files with hard-won lessons. Deleting a skill
deletes those lessons. The cold-store archive preserves the knowledge even when the skill itself
is no longer active.  
**Implication**: Every implementation must make the archive mechanism explicit. "Pruning" 
should be renamed "archiving" in student-facing materials.

## Known Failure Modes

| Failure | Trigger | Detection | Workaround |
|---|---|---|---|
| Procedure bloat | Users add more checks than they can realistically run | Procedure takes >30 min per skill | Identify the 2 mandatory steps (generalization test + pre-mortem); make the rest optional at lower thresholds |
| Governance without teeth | Rules exist but there's no enforcement mechanism | Skills keep getting registered without audit | Add a hard gate: skills cannot be retrieved until registration audit is logged |
| Overly broad merge | Merging produces a skill so general it triggers on everything | Merged skill is invoked 10× more than expected | Add precision requirement: merged skill must have a *tighter* trigger condition than either input |
| False quarantine | A skill enters quarantine because it wasn't invoked, not because it failed | Usage-based quarantine trigger fires on an undiscovered skill | Distinguish between "low-use" and "low-performing"; only flag the latter |

## When NOT to Use This Skill

- On skills with fewer than 5 total uses — too little data for meaningful drift analysis
- As a reason to delay registering genuinely useful skills — governance should enable deployment, not block it
- As a substitute for good skill creation in the first place — if the skill was designed badly, debt prevention treats the symptom, not the disease

## Improvement Ideas

- [ ] Add a "confidence interval" to the performance scorecard — not just average success rate but variance. A skill with 60% average but high variance is more dangerous than one with 50% average and low variance.
- [ ] Procedure 5 (Full Bank Audit) should auto-generate merge candidates, not just list overlapping pairs. The merge should be drafted, not just identified.
- [ ] Add a "skill genealogy" view: for any skill, show its parent (what skill it was created from or merged from). This makes historical context available during health reviews.
- [ ] The 14-day quarantine window was arbitrary in the first version. It should be calibrated to task frequency — a skill used daily needs a 3-day quarantine; one used monthly needs 60 days.

## Second-Order Implications of This Skill (Required Capstone Field — Teacher Reference)

If agents universally adopt skill-debt prevention:
- First order: skill banks stay compact and high-quality
- Second order: the cost of maintaining a large skill library stays sub-linear → more skills can be safely accumulated
- Third order: skill banks become long-lived institutional assets rather than ephemeral agent-specific tools — the "knowledge library" framing becomes literal

If they don't:
- First order: individual skills degrade over time
- Second order: the skill bank becomes a drag on performance rather than a boost
- Third order: teams abandon skill-based agents entirely and return to raw prompting — losing all compounding gains

## Governance Note (Required Capstone Field — Teacher Reference)

Proposed SkillHub rule: "Any skill with >1,000 total invocations across the network must pass
a Tier 2 audit (independent cross-agent validation + pre-mortem on the aggregated failure cases)
before it can continue to be distributed. High-impact skills get more scrutiny, not less."

Rationale: The skills that cause the most harm are the ones that are most widely used and least
frequently questioned. A reputation system that reduces scrutiny for popular skills inverts
the accountability model.
